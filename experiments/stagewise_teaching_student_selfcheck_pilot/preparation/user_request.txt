你是现有 Scene-RSI 项目的实验工程师。请直接在共享服务器上复用和修改现有代码，实际运行一个小型先导实验，生成真实图像、逐步轨迹和离线 HTML。不要只提供方案。

## 1. 这次研究什么

开发阶段：学生在同一个持续保存的场景中分阶段建模。每完成一个有意义的操作，教师读取原图、当前真实渲染及操作记录，给出具体纠错；学生修改当前场景，再继续下一阶段。

开发结束：把实际教学轨迹中的通用检查方法，整理成学生可执行的共享自检查流程。

测试阶段：教师完全退出。学生从空场景重建另一张图，在阶段间根据当前测试原图和自己的真实渲染主动检查、修正。

本轮研究的是在线教学与检查策略迁移，不是模型权重训练，也不声称完成教师自进化或证明新方法更好。

重要区别：不能把旧教师意见改写成第一人称，就声称测试学生自己发现了问题。测试时每项问题都必须对应测试图和当前输出中的实际证据。

## 3. 图片与模型在运行前固定

### 图片

D01：一张完整、连贯、有多个可辨识物体的场景，优先已有客厅或规整房间，便于展示主体家具的逐步创建。

T01：另一来源、另一布局的完整场景，优先已有规整厨房或其他房间，不能是D01裁剪、同一房间不同视角。

优先复用本地历史原图；避开人物主导、软件界面、拼图、局部产品、严重裁切或含糊编辑任务。

从已有manifest核对真实原图并在运行前确定，不根据本轮生成效果换题。已有历史曝光必须记录；“本轮教师未见T01”不等于“从未暴露的盲测”。

不要为了选图调用模型逐图排名。记录来源、原始路径、角色与此前是否使用过。

### 模型

沿用上一轮已跑通配置：
- 学生：gpt-6.1-terra / medium，通过现有 Codex CLI。
- 开发教师、开发轨迹提炼：gpt-6-astra / medium，通过现有 Codex CLI。

这次不再搜索或切换模型，不新增API Key。不用价格猜测声称降本。请求模型与可独立确认的实际路由分开记录，未知就unknown。

测试时的自检查由同一个学生模型完成，可以使用独立的学生检查调用，但模型与effort保持不变。不使用Astra或其他模型偷偷替学生审图。

## 4. 操作粒度：有意义的建模步骤，而不是每个bpy命令

先由学生针对D01制定一个简短阶段计划，通常4—5个阶段；教师只能在第一次场景构建后开始点评，不提前把完整答案写给学生。

可参考的通用阶段：
1. 房间/环境、相机与基础照明，得到可辨识的整体构图。
2. 主体家具或主要物体组：例如沙发、柜体、工作岛；先检查尺寸、朝向和投影。
3. 次要物体与关键空间关系、遮挡和间距。
4. 主要材质、灯光及必要部件。
5. 全局回看，修正已完成内容的明显不一致。

阶段按图片实际内容确定，不机械要求厨房也创建沙发。

一个操作可以是“创建主体沙发组”或“修改沙发比例与位置”，不能先完成整个场景再分文件伪装分阶段。

不要求每创建一个顶点、材质节点或小装饰就调用教师。局部对象变化影响全局相机或遮挡时，交付相应全局证据。

教师只对当前阶段已完成内容与其依赖点评，不因下一阶段尚未创建的物体处罚当前阶段。

## 5. 场景必须持续，纠错修改当前场景

这是对上一轮“每轮从空场景重建”的明确变更：
- D01只在开始时从空场景初始化一次。
- 同一任务内，后续阶段和纠错继续已有场景。
- T01另开干净工作区，从空场景初始化，与D01隔离。

优先用Blender加载上一步.blend，再运行增量patch，保存新检查点。保持对象ID、相机和已经完成的部件稳定。

可复用SceneAct初始化和构造，再以现有Blender接口修改对象；不需要重写SceneAct。

如果现有执行器每次都清空场景，给它增加明确的initial_blend/previous_checkpoint入口，不把重写整段完整答案冒充增量修改。

记录：父检查点、补丁、触及对象、创建/删除/修改内容、相机变化、构建结果和真实渲染。

每次改动保存独立检查点，失败时保留原成功场景，不让错误覆盖它。允许显式回退，记录原因，不按隐藏质量分挑最佳。

源码回放可以从初始场景依次应用补丁；不要求每次观测都重放全部历史代码。

## 6. 开发阶段：学生操作 → 真渲染 → 教师纠错 → 修改

执行顺序：
学生本阶段增量代码
→ Blender执行成功并保存检查点
→ 同一预览配置真实渲染
→ Astra教师查看参考图、当前渲染、上一检查点及简短操作记录
→ 输出具体问题、依据和建议
→ 学生局部修改或说明为什么不修改
→ 重新渲染
→ 教师确认改善/仍有问题
→ 进入下一阶段或记录未解决问题。

每阶段默认最多一次视觉纠错补丁。纠错后最多一次教师复核，不无限循环。

教师可返回：
- revise：当前步骤有需要优先修改的问题。
- advance：可继续下一阶段。
- advance_with_issue：预算内未解决，明确记录后继续。

这些是过程指导，不是质量分数，不据此宣称最终质量通过。

教师反馈简短具体，至多2—3项关键问题，包含：
- 当前目标对象/关系。
- 原图和当前渲染中可直接观察的差异。
- 建议修改什么，哪些已匹配内容不要动。
- 修改后应检查什么现象。
- 不确定的部分与需要的额外视图。

例如可以指出“沙发遮住了茶几；先检查画面占幅和前后关系，保持已对齐的墙角不变”，不要凭单图捏造精确真实尺寸。

教师只提供自然语言反馈，不直接替学生写场景补丁，不修改学生.blend。所有几何和代码修改由学生执行。

学生必须记录每项建议是落实、部分落实、未落实或不适用，并指向实际代码/场景变化；不要只写“已修复”。

### 执行错误与视觉错误分开

没有有效渲染时，先按实际异常修复程序，不允许教师凭空评价画面。

每阶段最多额外一次技术修复，计入总调用和构建预算，但它不等于已完成视觉纠错。

取得有效渲染后仍必须安排一次实际看图反馈；不能再次出现“第二次调用修完程序，就声称看图修订完成”。预算不够时记录visual_loop_incomplete，不能虚报该阶段完成。

## 7. 开发结束：只提炼通用自检查流程，不训练权重

D01结束后，使用一次Astra提炼调用，最多一次输出格式修正。此时Astra不能访问T01的像素、题目内容或其生成结果。

输入只包含D01的真实教学轨迹、学生修改记录、当前共享流程与公开工具接口。

产出：
1. self_check_policy.md：简短通用阶段检查规则，建议5—8条。
2. student_self_review.py或等价现有流程补丁：测试时实际触发学生观察和决策的入口。
3. lesson_provenance.json：每条规则对应的开发观察、教师反馈、实际修复与适用限制。

规则应写成通用问题或检查方法，例如：
- 比较主体物体的投影占幅、可见面、遮挡与固定环境锚点。
- 修改尺度前区分对象自身大小、位置深度和相机因素。
- 修改后回看已匹配对象，避免局部修复破坏整体。
- 判断执行错误、未生成、遮挡和画面外，不把它们混为一类。

不要把D01具体对象、坐标、颜色、数量、参考图路径或完整构造答案搬到测试。

不是把“教师发现沙发太宽”改成“我发现沙发太宽”后直接塞给T01。

禁止让提炼器凭空补写本次没发生的教学证据。原有通用规则与本轮从轨迹提炼的新增规则分开。

首次T01调用前，保存这份策略与执行代码的冻结快照。测试开始后不再调用Astra修改它，也不根据测试画面修改规则。

这一产物称为“教师指导提炼的学生自检查策略”，不是权重蒸馏、自动M1或已验证能力提升。

## 8. 测试阶段：教师退出，学生自己看图发现和修正

T01开始时，只提供：
- T01原图及固定公开任务。
- 同一场景执行工具。
- 冻结的通用自检查策略。

不提供D01图像、渲染、场景代码/.blend、完整教师对话、题目答案，不继续使用开发阶段的聊天会话。

同样采用4—5阶段。学生每次完成本阶段后：
1. 执行增量建模并真实渲染。
2. 用同一个学生模型读取T01原图、当前渲染和操作记录。
3. 根据通用方法检查当前结果，提出0—3个实际发现。
4. 决定是否局部修改，修改后再看实际结果。
5. 记录已解决、未解决或无法判断，然后继续。

没有真实问题时允许不改，不强迫每阶段制造一个错误。

自检查输出只记录可核查的观察、决定和简短理由，不要求内部思维链。

每条发现记录：
problem_source = test_observation
rule_source = 对应冻结规则或学生原有判断
reference_evidence / render_evidence
proposed_change / actual_change

只有来源为测试实际观察的问题，才可以说“学生在T01发现”。学习规则的来源仍如实注明教师。

测试模式任何Astra/teacher角色调用都应立即暴露为协议错误。不能将Astra重命名为student_reviewer继续使用。

本轮不进行A/B盲评，不调用自动质量评价器。技术执行检查可以继续，但不能用它证明视觉质量。

## 9. 小规模预算，明确两个任务不等于两帧

默认：
- 两张来源图、两个完整场景任务；每个最多5个主要阶段。
- 每阶段最多1次视觉纠错及其复核，额外最多1次程序错误修复。
- 全部新增CLI会话硬上限60：开发与提炼最多30，测试最多28，联通检查最多2。重试计入相同额度。
- 构建尝试总上限36，实际渲染帧上限80。
- 单CLI最长900秒；构建最长1200秒，渲染最长600秒。
- 每图活动总时限建议5400秒；排队时间另记。

预算是上限，不是消费目标。不恢复600秒整图期限，也不为了用满预算不断调用。

只开展一次D01和一次T01，不增加第三张图、不重抽结果、不自动产生下一教师版本。

渲染和补丁执行属于两个场景任务内的检查点，不报成几十次独立重建或独立样本。

服务路由失败先暂停并记录，不将外部服务故障解释为学生几何错误；最多使用现有一次瞬时重试规则。

预算耗尽时保存最后可用检查点及未完成状态，不能补写完整成功。

## 10. CPU多用一些，但遵守实际授权配额

先检查调度器、CPU affinity/cgroup及可用内存；不要将整机核数当成独占权限。

本轮用户允许多用CPU：若获准16核，使用单个Blender重任务×16线程；若仅8核就8线程。更多额度可测试16与24的真实收益，但不要为调参另开大型基准。

默认内存沿用32GB，获准更高时记录后使用。不要盲目扩大内存上限。

不硬编码CPU0–15，使用实际允许的CPU集合。

修改旧launch.py里固定8线程及backend各处线程参数，确保Blender、OMP/MKL/OpenBLAS均由同一配置下发。

同一场景的教学过程顺序执行。仅独立渲染视角可以在明确资源总额度内并行；不提前运行后续阶段来绕过教师反馈。

CPU资源不足不占用他人任务；不杀他人进程、不改驱动、不等待GPU。全程可CPU完成。

预览统一长边768、Cycles 16 samples；最终交付长边1024、32 samples。沿用已验证颜色管理，不更改风格来美化结果。

需要时提供一个目标对象裁剪，直接来自真实渲染；少量辅助视角计入80帧预算。不可使用生成式图片替代场景渲染。

记录CPU线程、进程树CPU时间、峰值内存、CLI等待、构建、渲染和报告耗时。增加CPU不会直接加速远端模型响应，分别报告。

## 11. CLI与研究隔离

沿用本地已验证adapter；核对codex --version和codex exec --help，不升级全局安装。

真实图片作为图像附件，不能只传文件路径并声称模型看过图。

每次记录角色、输入附件、允许目录、输出、JSONL、stderr、工具、用量、耗时。

一次exec可能包含多个可见动作，不能把会话数说成底层精确推理次数。无法观测的路由、费用和请求数留unknown。

一个场景内可以复用明确的学生上下文；D01与T01必须新会话隔离。跨进程延续时传当前检查点和有界事件摘要，不一次次发送整个历史目录。

教师/学生生成代码由共同runner执行。检查CLI是否另行私自运行Blender或读取其他实验；可见的额外动作全部记账。

不扩大读写权限，不提取认证信息，不修改全局AGENTS或账号配置。

## 12. 不使用自动评分，交付清楚的人工看图页面

关闭BW、VLM judge、Q、SSIM、LPIPS、DINO和自动质量排名。不调用模型判断谁更好。

教师在开发阶段看图纠错、学生在测试阶段自查是实验机制，不是外部评审。它们的判断可能错误，保留原文，不当作质量真值。

HTML必须本地完整可打开，含两张原图和全部阶段真实渲染，默认不依赖GitHub或远程图片。保留原图比例，支持点击放大。

分三部分：

A. 开发教学时间线
原图 → 本阶段首次结果 → 教师意见 → 学生修改 → 修改后结果 → 教师复核。
标注哪些是程序错误修复、哪些是视觉纠错，缺图留空并说明。

B. 教学经验怎样进入学生
实际开发反馈 → 被提炼的通用规则 → 对应共享流程补丁。
未被支持、被撤回或未迁移的意见也保留。

C. 测试学生自主纠错时间线
原图 → 本阶段首次结果 → 学生实际发现 → 冻结规则来源 → 局部修改 → 修改后结果。
明确显示“本任务教师调用数=0”，技术日志可展开。

每阶段展示目标对象、当前场景完成范围和短代码diff；不要只给最终两张图。

最终显示原图/最终渲染及可打开.blend。不要把不同图片的开发与测试结果排成同题胜负对照。

可提供用户填写“修正有帮助/无帮助/变差/无法判断”和备注并导出JSON，默认全未评。不得预填用户意见或自动宣判成功。

提供run、report、resume真实入口。resume只补未完成步骤，不从头重抽D01/T01，不自动新增样本或教师版本。

大日志与.blend沿用Release归档。完整带参考原图的看图包先保留本地；只有原图允许再分发时才公开打包，许可不明的提供本地完整包与公开路径清单，不私自再分发。

不上传凭证、模型缓存或权重，不做哈希验证。远端访问确认失败就如实标未确认。

## 14. 最终报告只回答真实发生的事

- 两张图是哪两张，为什么适合，历史是否暴露。
- D01教师在哪些阶段给了什么意见，学生是否落实。
- 哪些意见变成了共享自检查规则，哪些只是单图意见。
- T01学生实际发现了什么、改了什么；教师调用是否为0。
- 两个任务是否完成，阶段/修复/渲染分别多少，不混为独立样本。
- CPU和CLI各花多少时间，真实可见用量与未知项。
- 离线HTML、原图、逐步渲染、.blend、代码diff和Git提交位置。

这是一条在线教学与策略迁移的可行性案例。没有无教师同图对照、没有重复采样、没有权重训练、没有教师自进化收益证明。不宣称泛化变强或优于旧方法。
