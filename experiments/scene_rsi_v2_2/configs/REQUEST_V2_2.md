GitHub：
https://github.com/i025/scene

基于已经完成的 `research/scene-rsi-v2.1`，新建独立的 V2.2 实验分支。

本次目标不是继续增加 RSI 演化轮数，而是验证当前方法的两个核心科学问题：

1. V2.1 自动发现的共享重建算法修改，是否在独立图像上稳定有效？
2. 三维证据诊断是否真的提高了故障模块选择和共享程序修复能力？

直接检查代码、修复问题、运行实验、生成真实数据和可视化，最后上传 GitHub。不要只提供方案。

## 一、工程要求

优先复用现有 Scene-RSI、SceneEvolve、BlenderWorld 复现、Blender、SceneAct、模型和缓存。

不要重新下载已经能使用的模型。

不要重构整个项目。

代码风格保持一致，优先局部修改。

不要防御性编程，不要无意义的 fallback、多层 wrapper、到处 try/except 或复杂兼容框架。

不要进行 SHA、MD5、文件指纹、校验和验证。

保留 Git 版本、实际配置、运行日志和代码 diff 即可。

不覆盖 V1、V2、V2.1 的实验数据。

新实验使用独立目录和状态文件。

所有语言与视觉模型调用继续通过我的 Codex CLI：

- gpt-6.1-sol：场景重建。
- gpt-6-astra：诊断、共享程序修改、独立视觉评审。

沿用本地已经验证的模型名称、调用方式和 reasoning effort。

不要额外调用直接 API，不使用第三个模型。

不训练 GPT 基础模型。

## 二、实验 A：固定 V2.1 最优候选，验证实际收益

从 V2.1 真实候选目录加载：

- 初始重建流程 H0。
- r1/C2 的实际共享程序版本。

确认两者的真实源码、system.txt、运行配置和所依赖的 SceneAct 版本。

不从终测图像重新推导补丁，不手工优化候选。

固定这两个版本，禁止在本实验中继续修改 H/M。

这组实验只回答：

**r1/C2 是否真的比 H0 更可靠？**

### 实验设置

优先使用 6 个尚未用于此前开发、选择或人工分析的独立图像场景。

每个场景：

- H0 独立运行 2 次。
- r1/C2 独立运行 2 次。
- 同样的 Codex CLI 模型。
- 同样的内层执行、修复、渲染和时间预算。
- 同样的 SceneAct 和 Blender 环境。
- 同样的质量指标和外部评测。
- 交错运行两种 H，减少资源时间段差异。

计划共 24 次重建。

若资源预估不足，在正式开始前统一缩减到 4 个场景、每场景 2 次重复，共 16 次重建，并冻结调整。

不要看中途胜负再改变样本数。

不同模型调用重复不能视为完全独立的场景；统计中同时保留场景层级和运行重复。

若模型不支持固定采样种子，明确记录不可控的远端随机性。

数据划分按真实场景来源分组，不能把同一场景不同视角当作独立场景。

既有测试图像可以作为公开回顾案例，但不能再算新盲测。

### 核心指标

分别报告：

1. 可执行场景成功率。
2. 必需功能检查通过率。
3. 成功场景上的条件 Q。
4. 双方都成功时的配对 Q 差。
5. 全部任务的端到端效用，失败效用单独定义为 0。
6. 实际模型调用次数、token、Blender 执行与渲染成本。
7. 超时、构造失败和服务失败的分类。

不能把缺失的 PSNR、SSIM、LPIPS 或 DINO 值填成 0。

不能只展示成功场景。

重点调查 r1/C2 是否真的减少了过度复杂的 Mesh、昂贵的布尔操作或构造超时。

若执行成功率提高但 Q 下降，需要同时报告。

### 结论边界

此实验验证的是**已经通过 RSI 发现的固定共享程序修改**，不是重新验证 RSI 搜索方法优于通用框架。

即使 r1/C2 胜出，也不能把收益直接归因于三维诊断机制。

## 三、实验 B：改进三维诊断的第二阶段决策

检查：

- diagnostics.py
- strategies.py
- pilot.py
- regression.py
- 相关对象投影和代码轨迹模块。

保留 V2.1 的两阶段 M 接口：

M.plan_probes(context)

执行诊断

M.plan_patch(context, observations)

当前第二阶段不能主要依靠“哪个探测的 Q 提高最多”就决定故障模块。

改为让 M 明确记录：

- 当前观察到的错误。
- 两个或更多合理的候选解释（适用时）。
- 各解释预期对应的三维现象。
- 所选择的探测及其理由。
- 实际探测结果。
- 哪些解释获得支持、哪些未被区分。
- 证据能够支持的程序模块。
- 为什么修改该共享模块，而不是单场景参数。

不要求每次都有唯一正确原因。

证据不足时允许 unresolved。

### 修正失败分类

明确区分：

- Codex 服务失败或超时。
- Python 程序构造错误。
- Blender 场景构建错误。
- Blender 几何计算超时。
- 渲染阶段超时。
- 外层场景总预算耗尽。
- 结构或编辑回归失败。

依据真实步骤状态、错误日志与耗时分类，不单凭 build.py 是否存在判断。

不能将服务故障解释成三维算法失败。

### 修正修改后证据

候选修改前的图像定位结果属于历史证据。

修改后的场景若改变对象数量、名称或几何，不能直接把旧定位当作当前事实。

对后补诊断使用当前对象清单、代码 diff 和新回归结果。

确需重新视觉定位时，明确调用成本；预算不足就记录未重新定位。

不要根据代码 diff 中是否包含 mesh、scale 等字符串，宣称已经获得精确模块归因。

保留这些启发式时，明确标注为近似风险提示。

## 四、实验 C：已知故障的诊断机制验证

使用我们已有的 Continuous Mesh 和 SceneAct 环境，构造新的已知故障案例。

至少涵盖五类：

1. 相机焦距错误。
2. 家具尺度或位置错误。
3. 对象遗漏或错误遮挡。
4. 支撑及部件依赖错误。
5. 材质或局部编辑影响无关对象。

每类优先构造两个不同场景，共 10 个故障任务。

在任务建立时记录真实故障对象、注入的共享程序模块和预期行为。

这些真值仅提供给评价器，不能发送给被测试的 M。

被测 M 只能看到参考图像、重建结果、可公开对象与程序信息，以及共同的工具反馈。

### 诊断对照

比较：

A. V2.1 固定诊断启发式。

B. V2.2 证据驱动诊断。

这只是我们方法内部的机制消融，不是重新实现 Hyperagents 或 SceneEvolve。

同一批案例、相同可用工具和探测机会。

如果 V2.2 使用更多视觉模型调用，要记录真实额外成本，并在预算允许时增加同等调用额度的简单诊断对照。

不能声称调用数不同的两组拥有严格相同的计算预算。

### 指标

分别评价：

- 错误对象定位命中率。
- 故障模块定位命中率。
- 实际探测执行率。
- 探测是否区分候选解释。
- 第二阶段最终模块选择正确率。
- 共享程序修改后是否真正修复该故障。
- 修复是否能用于独立新场景。
- 完整诊断与修复成本。

“对象定位正确”不等于“程序模块定位正确”。

“模块定位正确”也不等于“共享程序修改有效”。

三者必须分开记录。

对于可有多个合理修复模块的故障，预先记录允许的模块集合，不在看结果后调整答案。

## 五、共享程序修复实验

在诊断任务上，可以允许 Codex 根据两组诊断输出修改事先注入缺陷的共享 H。

但必须保持：

- 同一个起始 H。
- 相同编码模型。
- 相同程序修改次数。
- 相同内层执行预算。
- 相同最终外部评价标准。
- 独立的修复验证场景。

不能只让 V2.2 使用编码模型，而固定启发式没有相同修改机会。

记录实际修改文件、diff、构造成功情况和独立修复结果。

禁止通过 task_id、参考图片路径或场景特例硬编码答案。

对局部参数修复和真正可跨场景复用的 H 修改分别标记。

如果诊断正确却没有产生有效 H，照实报告。

## 七、共享服务器约束

先查看当前服务器资源和调度情况。

不干扰其他用户任务。

只使用已获准的 GPU；GPU 空闲不等于自动获得使用权限。

最多一张 GPU。

没有获准且空闲的 GPU 时，优先 CPU 执行：

- Codex CLI 调用。
- 场景程序生成。
- Blender CPU 渲染。
- 几何检查。
- 数据分析与画图。

默认单个重任务、两个 CPU 计算线程，不超过实际分配。

不杀其他用户任务。

不修改驱动、全局 CUDA 或已有共享环境。

不为了 GPU 无限轮询。

复用现有环境与模型缓存。

正式成对实验使用一致的渲染质量和设备条件；如果因资源切换造成差异，单独标记。
